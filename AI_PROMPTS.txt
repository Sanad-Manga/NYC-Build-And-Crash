CONTEXT
Project: NYC Build and Crash (ICS503 Data Engineering and Visualization, Milestone 1, due 9 Nov). Story: do neighborhoods with the most new construction also become the most dangerous to walk, bike and drive in? Both datasets are aggregated to ZIP x year. Correlation only, never causation.
Repo: https://github.com/Sanad-Manga/NYC-Build-And-Crash. Create branch feature/website-skeleton off origin/main. Never commit to main, never force-push, do not edit other people's files.
Team rules: VS Code + venv only (no Colab), relative paths only, one shared requirements.txt (append pinned lines for new packages and say so in the PR), zip_code = 5-digit STRING, year = integer, borough values Title Case (Manhattan, Brooklyn, Queens, Bronx, Staten Island), scope 2022 onward (2026 is partial, ends 31 Oct).

STACK (assumed, confirm it against docs/SPEC.md if that file is on main; if SPEC says otherwise, stop and tell me): Streamlit + Plotly, later deployed on Render.

BUILD
1. data/dummy_zip_year.csv generated by a small script scripts/make_dummy_data.py (seeded, ~60 ZIPs across the 5 boroughs, years 2022-2026). Columns exactly: zip_code, year, borough, housing_job_count, new_building_count, collision_count, persons_injured, persons_killed, pedestrians_injured, cyclist_injured, motorist_injured, is_partial_year. Real-looking but clearly fake. The app must show a visible banner "DUMMY DATA" while this file is used.
2. src/data.py: load_data(path) reading zip_code as string, validating the schema and dtypes (raise a clear error otherwise). One place to switch to the real file later (data/zip_year.csv).
3. src/search.py: parse_query(text) -> dict(borough, year, metric, zip_code, unparsed). Rules: borough (case-insensitive, also "the bronx", "bk", "si", "nyc" = no filter), 4-digit year 2022-2026, 5-digit ZIP, metric keywords: "new buildings"/"new construction" -> new_building_count; "buildings"/"filings"/"jobs"/"housing" -> housing_job_count; "collisions"/"crashes" -> collision_count; "injuries"/"injured" -> persons_injured. Example: "Brooklyn 2022 new buildings" -> borough=Brooklyn, year=2022, metric=new_building_count. Unknown words are returned in `unparsed` and shown to the user ("Ignored: ..."). Add tests/test_search.py with at least 10 cases including that example, a ZIP, a typo, empty input.
4. app.py (Streamlit):
   - Sidebar: at least 3 dropdown filters (borough, year or "All years", metric) plus a ZIP multiselect, and a search box (search mode). A parsed search sets the filters and tells the user what it understood.
   - ONE central "Generate Report" button. Nothing on the page updates until it is clicked; clicking updates ALL visuals and the summary together (use st.session_state to hold the applied filters).
   - At least 4 varied interactive Plotly charts that all respond to Generate Report: (a) bar: top 10 ZIPs by chosen metric, (b) line: citywide trend by year (mark 2026 as partial), (c) scatter relating the two domains: new_building_count vs collision_count per ZIP (hover shows ZIP, borough; log or per-ZIP caveat noted), (d) grouped bar by borough. Every chart has a title, labelled axes with units, and a one-line caption.
   - A "Story" section with placeholders: question, findings, limitations (ZIP missing ~28% in collisions, partial 2026, no traffic-volume data, counts not normalised), NYC benefit. Wording must stay correlational.
5. README.md section "Run the website": venv, pip install -r requirements.txt, streamlit run app.py. Do not touch other README sections.

CODE QUALITY: modular (src/ for logic, app.py thin), commented, docstrings on public functions, no hardcoded absolute paths.
